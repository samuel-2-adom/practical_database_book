Transactions and Errors

What happens when something goes wrong halfway through? Transactions keep your data consistent, and exceptions tell you what failed. This chapter closes Part II.

What you will learn
  • What a transaction is and the four guarantees it gives (ACID)
  • How Python's sqlite3 opens, commits and rolls back transactions
  • A safe money-transfer function, with every failure case tested
  • The sqlite3 exception types, with the real messages they produce
  • Where to put try/except, and how constraints guard your data

13.1 What is a transaction?

A transaction is a group of statements that the database treats as one unit: either all of them take effect, or none do. The classic example is a bank transfer of GHS 500 from Ama to Kofi, which is two UPDATEs:

accounts during a transfer WITHOUT a transaction
MomentAmaKofiTotal money
Start10002001200
After step 1: deduct 500 from Ama500200700
Step 2 never runs (crash, power cut, bug)500200700
What should have happened5007001200

The yellow rows are the disaster: GHS 500 has vanished from the system. With a transaction, step 1 is only a draft until step 2 also succeeds. If anything fails in between, the draft is thrown away and Ama still has 1000.

13.2 The four guarantees (ACID)

LetterNameIn plain words
AAtomicityall or nothing: the transfer cannot be half-done
CConsistencythe data always obeys your rules (constraints) after a transaction
IIsolationwhile your transaction is a draft, others do not see its half-finished state (you saw this in Chapter 10)
DDurabilityonce committed, it survives crashes and power loss

You do not code ACID yourself. You get it by putting the related statements in one transaction, which is what this chapter shows.

13.3 When does a transaction start?

In Python's default mode you never write BEGIN. sqlite3 opens a transaction automatically right before your first INSERT, UPDATE or DELETE, and it stays open until you commit or roll back. SELECT does not open one. The connection's in_transaction flag lets you watch:

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE z (a)")

print(conn.in_transaction)          # False
conn.execute("INSERT INTO z VALUES (1)")
print(conn.in_transaction)          # True   a transaction opened by itself
conn.commit()
print(conn.in_transaction)          # False  closed by the commit

conn.execute("SELECT * FROM z")
print(conn.in_transaction)          # False  reading opens nothing

Two ways out of an open transaction: conn.commit() makes every statement since the start permanent; conn.rollback() throws them all away.

13.4 A safe transfer

Here is the accounts table. The CHECK rule makes a negative balance impossible at the database level (more in 13.7):

CREATE TABLE accounts (
    id      INTEGER PRIMARY KEY,
    owner   TEXT NOT NULL,
    balance REAL NOT NULL CHECK (balance >= 0)
);

And the transfer, using the nested with pattern from Chapter 10:

import sqlite3
from contextlib import closing

DB = "bank.db"

def transfer(from_id, to_id, amount):
    with closing(sqlite3.connect(DB)) as conn:      # closes the connection
        with conn:                                  # commit, or rollback on ANY exception
            cur = conn.execute(
                "UPDATE accounts SET balance = balance - ? WHERE id = ? AND balance >= ?",
                (amount, from_id, amount))
            if cur.rowcount == 0:
                raise ValueError("insufficient funds or unknown sender")

            cur = conn.execute(
                "UPDATE accounts SET balance = balance + ? WHERE id = ?",
                (amount, to_id))
            if cur.rowcount == 0:
                raise ValueError("unknown receiver")

How it works, step by step:

PieceWhy
AND balance >= ?checks the funds and deducts in one statement. If the money is not there, zero rows change and rowcount is 0.
if cur.rowcount == 0: raiseturns a silent “nothing happened” into a loud error
raising inside with connthe block sees an exception and rolls back, undoing the first UPDATE if the second one fails
no explicit commit()reaching the end of the with conn block without an error commits automatically

Test all three outcomes, starting with Ama 1000 and Kofi 200:

transfer(1, 2, 500)       # works
transfer(1, 2, 5000)      # ValueError: insufficient funds or unknown sender
transfer(1, 99, 100)      # ValueError: unknown receiver
balances after all three calls
ownerbalance
Ama500.0
Kofi700.0

The third call is the important one. Ama's 100 was deducted by the first UPDATE, but the receiver did not exist, so the exception rolled the deduction back. Ama still has 500, and no money was lost.

Redundant commit and rollback

You may see code like try: ...; conn.commit() except: conn.rollback(); raise wrapped inside a with block. The with already does both. Explicit commit() is only useful when you want to save a checkpoint mid-way, and rollback() when you want to undo without raising an error.

13.5 The sqlite3 exceptions

When SQLite refuses something, Python raises an exception from the sqlite3 module. They form a family, and you catch the one that matches the problem you can handle:

ExceptionTypical causeReal message
sqlite3.Errorbase class: catches every sqlite3 problem—
sqlite3.IntegrityErrora rule was broken: UNIQUE, NOT NULL, CHECK, FOREIGN KEYUNIQUE constraint failed: users.username
sqlite3.OperationalErrortable missing, SQL syntax error, database lockedno such table: nope
sqlite3.ProgrammingErrora mistake in your code, such as the wrong number of parametersIncorrect number of bindings supplied. The current statement uses 1, and there are 2 supplied.

The exact message is what you log or show: it names the table and column. Print it while you are learning:

try:
    conn.execute("INSERT INTO users (username, email) VALUES (?, ?)", ("a", "b@x"))
except sqlite3.Error as e:
    print(type(e).__name__, "-", e)
# IntegrityError - UNIQUE constraint failed: users.username

13.6 Where does the try/except go?

Put it outside the with. That order matters: when an error happens inside the block, the with rolls back first, then the exception travels up to your except. Your handler always sees a database that is already clean.

def add_user(username, email):
    try:
        with closing(sqlite3.connect("users.db")) as conn:
            with conn:
                conn.execute(
                    "INSERT INTO users (username, email) VALUES (?, ?)", (username, email))
        return True
    except sqlite3.IntegrityError as e:
        print(f"Cannot add user: {e}")           # e.g. UNIQUE constraint failed: users.email
        return False

Only IntegrityError is caught, because that is the one failure we can explain to the user (“that name is taken”). Anything else, such as a missing table, is a bug or an environment problem and should crash loudly so you notice.

Swallowing errors

except Exception: pass hides every problem, including bugs unrelated to the database. Catch the narrowest exception you can handle. If you catch something broad to log it, raise it again afterwards.

13.7 Constraints are your guard rails

The best error handling is a database that refuses bad data in the first place. Constraints do that, and break with IntegrityError:

ConstraintRefusesMessage
NOT NULLa missing valueNOT NULL constraint failed: users.username
UNIQUEa duplicateUNIQUE constraint failed: users.username
CHECK (balance >= 0)a value that breaks your ruleCHECK constraint failed: balance >= 0
FOREIGN KEYa link to a row that does not existFOREIGN KEY constraint failed
SQLite quirk: foreign keys are OFF by default

Unlike PostgreSQL, SQLite only enforces FOREIGN KEY if you turn it on, and you must do it on every new connection:

conn = sqlite3.connect(DB)
conn.execute("PRAGMA foreign_keys = ON")

conn.execute("INSERT INTO note_tags (note_id, tag_id) VALUES (99, 1)")   # note 99 does not exist
# IntegrityError - FOREIGN KEY constraint failed

Without that PRAGMA line, the insert above would succeed silently and leave a link pointing at nothing. If you use the connect() helper from Chapter 11, add the PRAGMA line there once. This is a good example of a difference between SQLite and PostgreSQL you will meet again in Chapter 17.

“database is locked”

SQLite allows one writer at a time. If two programs write at once, the second waits (5 seconds by default) and then raises OperationalError: database is locked. The fix is to keep transactions short: open, write, commit, close. Never leave a connection holding an uncommitted write while you wait for user input.

Exercises
Q1 — An exception is raised inside with conn: after one UPDATE has run. What happens to that UPDATE?
  • A It is saved anyway
  • B It is rolled back automatically
  • C The database file is deleted
The with block rolls the transaction back when an exception escapes, so the earlier UPDATE is undone.
Q2 — Which exception does a duplicate value in a UNIQUE column raise?
  • A sqlite3.IntegrityError
  • B sqlite3.OperationalError
  • C ValueError
Constraint violations (UNIQUE, NOT NULL, CHECK, FOREIGN KEY) raise IntegrityError. OperationalError is for structural problems such as a missing table or a syntax error.
Q3 — Why is UPDATE ... SET balance = balance - ? WHERE id = ? AND balance >= ? better than a SELECT followed by an UPDATE?
  • A It is shorter to type
  • B It checks and changes the balance in a single step, so the check cannot go stale
  • C It avoids needing a transaction
With separate SELECT and UPDATE, the balance could change between the two steps. One statement makes the check and the change atomic. You still need the transaction to cover both UPDATEs of the transfer.
Q4 — Where should the try/except sqlite3.IntegrityError go relative to the with block?
  • A Inside it, around each execute
  • B Outside it, so the rollback happens before the handler runs
  • C It does not matter
Outside. The with block rolls back as the exception leaves it, so your handler always runs against a clean database.
Part II checkpoint: transfer

Write transfer(from_id, to_id, amount) from memory. It must (1) refuse overdrafts, (2) refuse an unknown receiver and undo the withdrawal in that case, and (3) refuse a non-positive amount before touching the database. Then test all three failures and check the balances did not change.

def transfer(from_id, to_id, amount):
    if amount <= 0:
        raise ValueError("amount must be positive")      # checked before any SQL
    with closing(sqlite3.connect(DB)) as conn:
        with conn:
            cur = conn.execute(
                "UPDATE accounts SET balance = balance - ? WHERE id = ? AND balance >= ?",
                (amount, from_id, amount))
            if cur.rowcount == 0:
                raise ValueError("insufficient funds or unknown sender")
            cur = conn.execute(
                "UPDATE accounts SET balance = balance + ? WHERE id = ?", (amount, to_id))
            if cur.rowcount == 0:
                raise ValueError("unknown receiver")      # triggers rollback of the withdrawal
