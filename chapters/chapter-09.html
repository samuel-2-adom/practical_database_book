9.1 Aggregate functions

A normal query returns one output row per input row. An aggregate function reads many rows and returns one value.

FunctionReturns
COUNT(*)how many rows
COUNT(col)how many rows where col is not NULL
SUM(col)total of the values
AVG(col)average of the values
MIN(col)smallest value
MAX(col)largest value

You can use several in one query. AS gives each result column a readable name:

SELECT COUNT(*)            AS n,
       SUM(amount)         AS total,
       ROUND(AVG(amount), 2) AS average,
       MIN(amount)         AS smallest,
       MAX(amount)         AS largest
FROM expenses;
Result (all 6 rows collapsed into 1)

6249.041.58.0112.3

Aggregates see only the rows that survive WHERE. WHERE runs first, then the aggregate:

SELECT SUM(amount) FROM expenses WHERE category = 'Food';   -- 186.0  (25.50 + 112.30 + 48.20)
SELECT COUNT(DISTINCT category) FROM expenses;               -- 3  (unique categories)

NULL: the quiet trap

Aggregates skip NULLs, except COUNT(*), which counts rows regardless. Imagine a table where one score was never entered:

9.2 GROUP BY — one result per category

Without GROUP BY, an aggregate squashes everything into one row. GROUP BY first sorts the rows into buckets by a column's value, then runs the aggregate inside each bucket.

SELECT category,
       COUNT(*)    AS n,
       SUM(amount) AS total
FROM expenses
GROUP BY category
ORDER BY total DESC;

The GROUP BY rule

Every column in your SELECT must be either listed in GROUP BY or wrapped in an aggregate. Why? Each bucket collapses to one row, so a column like item has no single answer (is it Lunch, Groceries or Dinner?).

SQLite will not stop you from breaking this rule: it silently picks an arbitrary row. PostgreSQL raises an error instead. Treat the rule as strict in both.

Grouping by two columns

FROM tasks
GROUP BY priority, status

9.3 WHERE vs HAVING — it is all about order

SQL does not run your query top to bottom as you wrote it. It runs the clauses in this fixed order:

1 · FROM / JOINPick the tables and combine them.
2 · WHEREThrow away individual rows.
3 · GROUP BYSort what is left into buckets.
4 · HAVINGThrow away whole buckets.
5 · SELECTCompute the columns and aggregates.
6 · ORDER BYSort the result.
7 · LIMITCut it to N rows.

That order explains the rule: WHERE runs before any bucket exists, so it cannot see a SUM or COUNT. HAVING runs after the buckets are built, so it can.

SELECT category, SUM(amount) AS total
FROM expenses
WHERE amount > 10                -- step 2: drop small expenses (rows)
GROUP BY category                -- step 3: bucket by category
HAVING SUM(amount) > 40          -- step 4: drop weak categories (buckets)
ORDER BY total DESC;

Rule of thumb

Condition about a single row (amount > 10, status = 'pending')? → WHERE. Condition about a group's total (COUNT(*) > 3, SUM(...) > 40)? → HAVING. Prefer WHERE whenever possible: it shrinks the data before the expensive grouping.

SQLite lets you write HAVING total > 40 using the alias. PostgreSQL does not, so repeat the aggregate (HAVING SUM(amount) > 40) and your code works in both.

The LEFT JOIN counting trap

For ideas, the LEFT JOIN produces one row with nt.note_id = NULL. COUNT(*) counts that row and reports 1 (wrong). COUNT(nt.note_id) skips the NULL and correctly reports 0. After a LEFT JOIN, count a column from the right-hand table.

9.5 CASE WHEN — if/else inside SQL

CASE looks at a row and returns one value depending on conditions, like Python's if / elif / else but as an expression you can put almost anywhere in a query.

CASE
    WHEN condition1 THEN result1
    WHEN condition2 THEN result2
    ELSE fallback            -- optional; without it you get NULL
END

Rules: conditions are checked top to bottom and the first match wins; END is required; give the whole thing an AS name when it is in SELECT.

Use 1 — label rows

SELECT item, amount,
       CASE
           WHEN amount >= 40 THEN 'big'
           WHEN amount >= 20 THEN 'medium'
           ELSE 'small'
       END AS size
FROM expenses;
itemamountsize
Lunch25.5medium
Bus fare8.0small
Groceries112.3big
Taxi35.0medium
Airtime20.0medium
Dinner48.2big

Groceries (112.3) matches the first WHEN and stops, so it never reaches the second test. Order your WHENs from most specific to least.

Use 2 — custom sort order

Plain ORDER BY priority sorts alphabetically (high, low, medium). CASE turns each word into a number so you control the order:

SELECT title, priority FROM tasks
ORDER BY CASE priority
             WHEN 'high'   THEN 1
             WHEN 'medium' THEN 2
             WHEN 'low'    THEN 3
         END;

This is the “simple form”: CASE column WHEN value THEN ... compares one column to several exact values. The first form (CASE WHEN condition) handles ranges and any condition.

Use 3 — conditional counting (the dashboard trick)

This is the one that confused you, so let us take it slowly. Goal: for each priority, how many tasks are complete? Inside an aggregate, CASE turns each row into a 1 (counts) or a 0 (does not), and SUM adds them up:

SUM(CASE WHEN status = 'complete' THEN 1 ELSE 0 END)

Take the three high tasks. First CASE runs on every row; then SUM adds each bucket:

9.6 A real dashboard query, piece by piece

Now the query has no mystery left. Task count, completed count and completion percentage per priority, most urgent first:

SELECT
    priority,
    COUNT(*)                                          AS total,
    SUM(CASE WHEN status = 'complete' THEN 1 ELSE 0 END) AS done,
    ROUND(100.0 * SUM(CASE WHEN status = 'complete'
                           THEN 1 ELSE 0 END) / COUNT(*), 1) AS pct_done
FROM tasks
GROUP BY priority
ORDER BY CASE priority
             WHEN 'high'   THEN 1
             WHEN 'medium' THEN 2
             WHEN 'low'    THEN 3
         END;
prioritytotaldonepct_done
high3133.3
medium3133.3
low2150.0
PieceWhat it does
GROUP BY priorityone bucket each for high, medium, low
COUNT(*)rows in the bucket = total tasks
SUM(CASE ... END)conditional count = completed tasks (9.5, use 3)
100.0 * ... / COUNT(*)percentage. The 100.0 matters: in SQLite 1 / 3 is 0 (integer division), but 100.0 * 1 / 3 is 33.33...
ROUND(..., 1)keep one decimal place
ORDER BY CASE ...logical order instead of alphabetical (9.5, use 2)
Five mistakes to recognise

1) Using an aggregate in WHERE (use HAVING). 2) Selecting a column that is neither grouped nor aggregated. 3) Using COUNT(*) after a LEFT JOIN and counting the empty match. 4) Forgetting that aggregates skip NULL. 5) Integer division: done / total gives 0; multiply by 100.0 first.

Exercises
Q1 — What is the difference between WHERE and HAVING?
  • A They are identical
  • B WHERE is for text; HAVING is for numbers
  • C WHERE filters rows before grouping; HAVING filters groups after aggregation
WHERE runs before GROUP BY, so it filters raw rows and cannot see aggregates. HAVING runs after, so it filters buckets and can use COUNT, SUM and the rest.
Q2 — A table has scores 80, NULL, 70. What does AVG(score) return?
  • A 50.0
  • B 75.0
  • C NULL
AVG skips NULL, so it computes 150 / 2 = 75. Use AVG(COALESCE(score, 0)) to treat NULL as 0 (result: 50).
Q3 — After a LEFT JOIN, which expression correctly counts a tag with no notes as 0?
  • A COUNT(*)
  • B COUNT(nt.note_id)
  • C COUNT(t.id)
The unmatched tag gets one row where nt.note_id is NULL. COUNT(*) counts that row (1). COUNT(nt.note_id) skips the NULL (0). COUNT(t.id) also counts it, because t.id is never NULL.
Q4 — What does SUM(CASE WHEN status = 'complete' THEN 1 ELSE 0 END) compute?
  • A The sum of the status column
  • B The number of rows where status is 'complete'
  • C The number of distinct statuses
CASE converts every row to 1 (complete) or 0 (anything else). SUM adds those, which equals the number of complete rows.
