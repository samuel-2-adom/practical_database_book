Part II — SQLite + Python · Chapter 10

Intro to sqlite3

Part II starts here. You already know SQL; now you run it from Python. This chapter slows down on every moving part (connection, cursor, commit, fetch and with) so none of it feels like magic.

What you will learn
  • What a connection, a cursor and a transaction each are
  • What execute, fetchall and commit actually do (and when you need each)
  • Why changes disappear if you forget to commit
  • What with sqlite3.connect() really does, and what it does not do
  • A clean, safe pattern for every database function you write
SQLite: no setup needed

sqlite3 ships with Python. No install, no server. The whole database is one .db file that is created automatically the first time you connect.

10.1 The big picture

Think of the database file as a library. You do not walk around the shelves yourself; you go through a process:

The librarian at the deskcursortakes your requests and holds the books you asked for
Your request slipexecute("SQL")one SQL statement

1 · connectOpen the file. You get a connection.
2 · cursorCreate the object that runs SQL and holds results.
3 · executeSend one SQL statement.
4 · fetch or commitReading? fetch the rows. Writing? commit the change.
5 · closeHang up. Release the file.

The key idea: reading and writing finish differently.

10.2 Connecting

import sqlite3

conn = sqlite3.connect("tasks.db")    # creates the file if it does not exist
conn.close()

conn = sqlite3.connect(":memory:")    # a throwaway database in RAM, gone on exit
Where did my .db file go?

A bare name like "tasks.db" is created in the folder you ran Python from, not necessarily where the script lives. If you cannot find your file, print os.getcwd(). Use ":memory:" for experiments you do not want to keep.

10.3 The cursor

A cursor is the object that sends SQL to the database and holds the rows that come back. You create it from the connection:

conn = sqlite3.connect(":memory:")
cursor = conn.cursor()
cursor.execute("CREATE TABLE tasks (id INTEGER PRIMARY KEY, title TEXT NOT NULL, status TEXT NOT NULL)")
cursor.execute("INSERT INTO tasks (title, status) VALUES ('Write report', 'pending')")

Because creating a cursor every time is repetitive, the connection has a shortcut: conn.execute(...) makes a cursor behind the scenes, runs your SQL, and hands the cursor back. These two lines do the same thing:

conn.cursor().execute("SELECT * FROM tasks")
conn.execute("SELECT * FROM tasks")           # shortcut, used from now on

10.4 Reading: execute, then fetch

execute("SELECT ...") runs the query, but the rows are waiting inside the cursor. They are not in your variables yet. A fetch method moves them into Python:

conn.executemany("INSERT INTO tasks (title, status) VALUES (?, ?)",
                 [("Write report", "pending"), ("Email Kwame", "complete")])

cur = conn.execute("SELECT id, title, status FROM tasks")
rows = cur.fetchall()
print(rows)
# [(1, 'Write report', 'pending'), (2, 'Email Kwame', 'complete')]
MethodWhat you get
fetchall()a list of all remaining rows; each row is a tuple
fetchone()the next single row (a tuple), or None when finished
fetchmany(n)up to n rows
for row in cur:loops through rows one at a time without building a big list
A cursor is used up once you read it

Rows are handed out once. After cur.fetchall(), calling cur.fetchall() again returns []. If you need the data twice, store it in a variable the first time.

Rows are plain tuples, so you read them by position (row[1] is the title). In Chapter 11 you will meet sqlite3.Row, which lets you use column names instead.

10.5 Writing: transactions and commit

When you run INSERT, UPDATE or DELETE, SQLite does not write straight to the file. It opens a transaction: a private draft that only your connection can see. commit() publishes the draft to the file. Until then, the change is not saved and nobody else sees it.

You can watch it happen with two connections to the same file:

a = sqlite3.connect("demo.db")
b = sqlite3.connect("demo.db")          # a second, independent connection
a.execute("CREATE TABLE IF NOT EXISTS n (t TEXT)")
a.commit()

a.execute("INSERT INTO n VALUES ('hi')")
print(a.execute("SELECT COUNT(*) FROM n").fetchone())   # (1,)  a sees its own draft
print(b.execute("SELECT COUNT(*) FROM n").fetchone())   # (0,)  b sees the file: nothing yet

a.commit()
print(b.execute("SELECT COUNT(*) FROM n").fetchone())   # (1,)  now it is published
StepYour connection (a) seesThe file / other connections see
a.execute(INSERT ...)1 row (your draft)0 rows
a.commit()1 row1 row: saved
a.rollback() instead of commit0 rows: draft thrown away0 rows
No commit = no save

If your program ends, or the connection closes, while a transaction is still open, SQLite throws the draft away. This is the most common “my data vanished” bug. The fix is a commit, or letting with do it for you (next section).

10.6 What with actually does

with sqlite3.connect("tasks.db") as conn:
    conn.execute("INSERT INTO tasks (title, status) VALUES ('Plan sprint', 'pending')")
# leaving the block: commit() if no error, rollback() if an exception happened

So with with, you do not write conn.commit() yourself. The block commits when it ends normally and rolls back everything if an error is raised, so you never save half a job.

Plain connectionwith sqlite3.connect() as conn
commityou must call conn.commit()automatic on success
rollback on erroryou must call conn.rollback()automatic
execute / fetchallneededstill needed: for reading you still use them
close the connectionyou must call conn.close()NOT done: with only handles the transaction
with does not close the connection

It is easy to assume it does, but with on a sqlite3 connection only commits or rolls back. To also close, wrap it with contextlib.closing, as in the next section.

10.7 The safe pattern

import sqlite3
from contextlib import closing

DB = "tasks.db"

def init_db():
    with closing(sqlite3.connect(DB)) as conn:   # outer: closes the connection
        with conn:                               # inner: commit / rollback
            conn.execute("""
                CREATE TABLE IF NOT EXISTS tasks (
                    id         INTEGER PRIMARY KEY,
                    title      TEXT NOT NULL,
                    status     TEXT NOT NULL DEFAULT 'pending',
                    priority   TEXT NOT NULL DEFAULT 'medium',
                    created_at TEXT NOT NULL
                )""")
    print(f"Ready: {DB}")

init_db()

Read it from the inside out: the inner with conn guards the transaction, the outer closing(...) guarantees the connection is shut. Use this shape for every database function from now on.

Two mistakes worth recognising

# MISTAKE 1: writing AFTER the with block has already committed
def get_db():
    with sqlite3.connect(DB) as conn:
        cursor = conn.cursor()
        return cursor            # with ends here: commit happens NOW

cur = get_db()
cur.execute("INSERT INTO tasks (title, created_at) VALUES ('x', 'today')")
# This INSERT starts a NEW transaction that nobody commits -> lost on exit.

# MISTAKE 2: returning a cursor instead of the data
# If the connection is closed or goes away, the cursor is useless.
# Fetch inside the function and return a plain list instead:
def all_tasks():
    with closing(sqlite3.connect(DB)) as conn:
        return conn.execute("SELECT * FROM tasks").fetchall()

The rule behind both: do all your SQL work inside the function that owns the connection, and hand back data, not cursors or connections.

Exercises
Q1 — What happens when you connect to a .db file that does not exist?
  • A FileNotFoundError is raised
  • B SQLite creates the file automatically
  • C It returns None
sqlite3.connect creates the file for you. This is why a typo in the filename silently gives you a new, empty database.
Q2 — Which statement needs fetchall() to see its results?
  • A INSERT
  • B SELECT
  • C DELETE
Only SELECT returns rows. They wait inside the cursor until you fetch them. INSERT, UPDATE and DELETE return nothing to fetch; they need a commit instead.
Q3 — You run an INSERT and the program ends without a commit. What happens to the row?
  • A It is saved anyway
  • B It is lost: the open transaction is discarded
  • C SQLite raises an error
Changes live in an open transaction until commit(). No commit means the draft is discarded when the connection goes away.
Q4 — What does with sqlite3.connect(DB) as conn: do when the block finishes without error?
  • A Commits the transaction (but does not close the connection)
  • B Closes the connection only
  • C Commits and closes the connection
The with block manages the transaction: commit on success, rollback on exception. It does not close the connection; use contextlib.closing for that.
Try it

Write init_db() that creates a notes table (id, title, content, created_at) using the safe pattern. Then write add_note(title, content) and get_notes(). Run them and confirm the rows are still there after you restart Python.

import sqlite3
from contextlib import closing
from datetime import datetime

DB = "notes.db"

def init_db():
    with closing(sqlite3.connect(DB)) as conn:
        with conn:
            conn.execute("""
                CREATE TABLE IF NOT EXISTS notes (
                    id INTEGER PRIMARY KEY AUTOINCREMENT,
                    title TEXT NOT NULL,
                    content TEXT NOT NULL,
                    created_at TEXT NOT NULL)""")

def add_note(title, content):
    with closing(sqlite3.connect(DB)) as conn:
        with conn:
            conn.execute(
                "INSERT INTO notes (title, content, created_at) VALUES (?, ?, ?)",
                (title, content, datetime.now().isoformat()))

def get_notes():
    with closing(sqlite3.connect(DB)) as conn:
        return conn.execute("SELECT id, title, content FROM notes").fetchall()

init_db()
add_note("Sleep", "Sleep is good for the soul")
print(get_notes())
