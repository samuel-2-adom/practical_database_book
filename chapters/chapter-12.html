Parameterised Queries

The question marks you have been using are not just convenient: they are what keeps your database safe. See the attack work, then see the fix.

What you will learn
  • Why SQL built from strings is dangerous, shown with real attacks
  • How ? placeholders make injection impossible
  • What placeholders can and cannot do (table names, LIKE, IN)
  • Named parameters, and executemany for batches

12.1 SQL is just text

When you call execute("..."), the database receives text and works out which parts are commands (SELECT, WHERE, OR) and which are data ('Samuel'). If you build that text with an f-string, a user's input becomes part of the text, and the database cannot tell your code from their input.

Building with an f-string

name = input()
→ user types: x' OR '1'='1
↓
text = f"... WHERE name = '{name}'"
↓
... WHERE name = 'x' OR '1'='1'
↓
Database parses this as code: the OR is a command
↓
Every row comes back

Using a ? placeholder

name = input()
→ user types: x' OR '1'='1
↓
sql = "... WHERE name = ?" (fixed text)
↓
params = (name,) (sent separately)
↓
Database already parsed the SQL. The input is only a value
↓
Looks for a name literally equal to that odd string: no rows

12.2 Watch the attack work

Here is a deliberately bad login function. Run it yourself in a scratch file:

import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT, password TEXT)")
conn.executemany("INSERT INTO users (name, password) VALUES (?, ?)",
                 [("ama", "pw1"), ("kofi", "pw2")])

def bad_login(name, password):                      # DO NOT WRITE CODE LIKE THIS
    sql = f"SELECT * FROM users WHERE name = '{name}' AND password = '{password}'"
    print("RUNNING:", sql)
    return conn.execute(sql).fetchone()

bad_login("ama", "wrong")        # None: correct, login refused

Attack 1: bypass the password

bad_login("ama", "' OR '1'='1")
# RUNNING: SELECT * FROM users WHERE name = 'ama' AND password = '' OR '1'='1'
# -> (1, 'ama', 'pw1')   logged in without knowing the password!

Why it works: SQL evaluates AND before OR, so the condition reads (name is ama AND password is empty) OR (1 equals 1). The second half is always true, so every row qualifies.

Attack 2: comment out the password check

bad_login("ama' --", "anything")
# RUNNING: SELECT * FROM users WHERE name = 'ama' --' AND password = 'anything'
# -> (1, 'ama', 'pw1')

-- starts an SQL comment, so everything after it, including the password test, is ignored.

Attack 3: read data you never meant to expose

def bad_search(term):
    return conn.execute(f"SELECT id, name, password FROM users WHERE name = '{term}'").fetchall()

bad_search("x' UNION SELECT id, name, password FROM users --")
# [(1, 'ama', 'pw1'), (2, 'kofi', 'pw2')]   every row, passwords included
“But DROP TABLE does not work in sqlite3?”

True: sqlite3's execute refuses two statements at once (ProgrammingError: You can only execute one statement at a time). Do not take comfort from that. Attacks 1 to 3 need only one statement, and other databases and drivers do allow stacked statements.

12.3 The fix: placeholders

def good_login(name, password):
    return conn.execute(
        "SELECT * FROM users WHERE name = ? AND password = ?",
        (name, password),
    ).fetchone()

good_login("ama", "' OR '1'='1")        # None   the attack is just a wrong password
good_login("ama' --", "anything")       # None   no user is literally named  ama' --

The ? marks a slot. The SQL text is parsed first, with the slots empty, so its structure is locked in. Your values are sent separately and slotted in as pure data. No quote or OR inside them can change what the query means. The same code that was wide open in 12.2 is now safe.

DetailWhy it matters
Parameters go in a tuple: (name,)A single value needs the trailing comma. (name) is just a string in brackets and will fail or misbehave.
One ? per valueCount must match: otherwise ProgrammingError: Incorrect number of bindings.
Never put quotes around ?Write name = ?, not name = '?'. sqlite3 handles the quoting.
Works for every statementSELECT, INSERT, UPDATE and DELETE all take parameters the same way.
No exceptions

Not f-strings, not % formatting, not + concatenation, not .format(). This applies to any outside value: user input, file contents, API data, even values from your own database.

12.4 What a placeholder cannot do

Placeholders stand in for values only. They cannot replace table or column names, because the database must know the structure before it runs the query:

conn.execute("SELECT * FROM ? WHERE id = 1", ("tasks",))      # ERROR: a table name is not a value

If a column or table name must vary, choose it from a fixed list you control (a whitelist), never from raw input:

ALLOWED_SORTS = {"title", "status", "priority", "created_at"}

def list_tasks(sort_by):
    if sort_by not in ALLOWED_SORTS:
        raise ValueError("bad sort column")
    return conn.execute(f"SELECT * FROM tasks ORDER BY {sort_by}").fetchall()   # safe: checked first

LIKE searches

The % wildcards belong inside the value, not the SQL:

term = "sleep"
conn.execute("SELECT * FROM notes WHERE title LIKE ?", (f"%{term}%",))

IN lists

You need one ? per item. Generating the question marks is safe because you build only ? characters, never user text:

ids = [1, 3, 5]
marks = ",".join("?" * len(ids))            # "?,?,?"
conn.execute(f"SELECT * FROM tasks WHERE id IN ({marks})", ids)

12.5 Named parameters

With many values, positional ? gets hard to read. Name each slot with :name and pass a dictionary:

from datetime import datetime

task = {
    "title":    "Learn parameterised queries",
    "priority": "high",
    "status":   "pending",
    "created":  datetime.now().isoformat(),
}

conn.execute(
    """INSERT INTO tasks (title, priority, status, created_at)
       VALUES (:title, :priority, :status, :created)""",
    task,
)

12.6 executemany: batch inserts

tasks = [
    ("Task one",   "high",   "2026-01-01"),
    ("Task two",   "medium", "2026-01-02"),
    ("Task three", "low",    "2026-01-03"),
]

with sqlite3.connect("tasks.db") as conn:
    conn.executemany(
        "INSERT INTO tasks (title, priority, created_at) VALUES (?, ?, ?)",
        tasks,
    )

The SQL is parsed once and run once per tuple, which is faster than a Python loop and still fully safe.

Your safety checklist

Before every execute, ask: is any value from outside typed into the SQL string? If yes, replace it with ? and move it into the tuple. If a name must vary, whitelist it.

Exercises
Q1 — What is SQL injection?
  • A A way to speed up queries
  • B Malicious SQL inserted through input that gets mixed into your query text
  • C A Python error type
It happens when input is concatenated into the SQL string, so the database treats the attacker's text as code. Placeholders keep values and SQL separate.
Q2 — Which is the safe way to include task_id?
  • A conn.execute(f"SELECT * FROM tasks WHERE id = {task_id}")
  • B conn.execute("SELECT * FROM tasks WHERE id = " + str(task_id))
  • C conn.execute("SELECT * FROM tasks WHERE id = ?", (task_id,))
Only C uses a placeholder. A and B build the SQL text from the value, which is the injection pattern.
Q3 — You want users to choose which column to sort by. Can you use ORDER BY ??
  • A Yes, placeholders work for any part of the query
  • B No: placeholders are for values, so check the column against a whitelist instead
  • C Yes, but only with named parameters
Placeholders can only stand for values, not identifiers like column names. Validate the name against a fixed set, then put it in the SQL.
Q4 — Why does conn.execute(sql, (name)) misbehave?
  • A It is fine
  • B (name) is not a tuple: you need (name,)
  • C execute never accepts parameters
Brackets alone do not make a tuple; the comma does. Without it Python passes a plain string and sqlite3 treats each character as a separate parameter.
Checkpoint

Rewrite this unsafe function so it is safe, and make it return a list of dicts:
def find_task(name): conn.execute(f"SELECT * FROM tasks WHERE title = '{name}'")

def find_task(name):
    with sqlite3.connect("tasks.db") as conn:
        conn.row_factory = sqlite3.Row
        cur = conn.execute("SELECT * FROM tasks WHERE title = ?", (name,))
        return [dict(r) for r in cur.fetchall()]
